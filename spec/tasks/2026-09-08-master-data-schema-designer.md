# Pf にマスターデータ専用のスキーマ設計 UI を用意する

## 目的

neco の指示: データスキーマにはマスターデータとユーザーデータがある。ユーザーデータの保存先設計は今回作成する UI で対応できるが、マスターデータを設計する場所がないため、Pf に専用の設計画面を設ける。

施設一覧・商品マスタ・ゲームのアセット定義など、参照中心のマスターデータについて、項目と制約、関連、正本の管理者、利用先を設計できるようにする。ユーザーデータの保存先選択や既存画面の master 分類だけで代替しない。

## 作業

1. Pf のプロジェクトから「マスターデータ設計」へ進む専用の導線を設け、マスター定義の一覧・追加・編集を用意する。画面名と説明でユーザーデータ設計との用途を明確にする。
2. マスターごとに識別名・表示名・目的・権威ソース・更新責任者・利用ドメインを定義できるようにする。
3. 項目の型、必須、主キー、一意制約、列挙値、既定値、他マスターへの参照を設計できるようにする。複数レコードを前提にし、Cr の 1 ユーザー 1 行や module / column をマスターの制約にしない。
4. マスター同士、およびユーザーデータからマスターへの参照方法を定義する。安定 ID を使い、名称変更で参照を壊さず、削除前に参照元と影響を表示する。
5. 型と既定値・列挙値の整合、識別名と主キーの重複、存在しない参照、不足した権威ソースを検査する。既定値を SQL 式として受け取らない。
6. マスターの正本と利用先への提供方法を設計として記入できるようにする。配布形式・更新単位・利用側が参照する版を整理し、実行時の配布処理やデータ移行とは区別する。
7. 定義の保存・再読込・版管理・差分確認・設計書出力を用意する。保存スキーマは実装前に spec へ記載し、PostgreSQL / 明示 local mode の SQLite とプロジェクト認可に対応する。
8. 今回のユーザーデータ設計との共通契約・参照関係を整理する。既存の設計を勝手に変換せず、移行が必要なら互換性と影響を先に文書化する。

## 完了条件

- プロジェクトからマスターデータ専用画面へ進み、マスターとその項目・制約・関係を設計できる。
- 例として商品マスタとカテゴリマスタの定義、商品からカテゴリへの参照を保存・再読込・出力できる設計になっている。
- マスターの権威ソース・更新責任者・提供方法が明示され、ユーザーごとの保存領域入力を要求しない。
- 不正な型・重複・参照切れを検出し、同時編集や取得失敗で保存済みの定義を上書きしない。
- 閲覧・更新はプロジェクト所属と役割に従い、実データ・credential を設計メタデータへ混在させない。
- ユーザーデータ設計と専用マスター設計の境界を UI・spec の両方に記載する。
- 実行した静的確認と、許可後に実施したテストだけを結果として報告する。未実施の動作確認を成功扱いしない。

## 今回のタスクに含めないもの

Cr の保存領域変更、認証基盤の変更、稼働 DB への自動適用、マスターレコードの本番編集・配布・移行は対象外。ここで設計した定義を消費する実行系や、実値を編集する管理画面が必要なら別の作業として扱う。
