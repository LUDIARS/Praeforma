# Pfのスクラム支援と再構築自動化：設計提案

状態：提案のみ。スクラム機能・自動化の実装は今回の対象外。

## 目的と前提

デファードプランニングでは、試行中の判断を断片として蓄積し、適切な区切りで体系へ整理する。
Pfが整理のタイミングと未決事項を可視化し、スクラムの進行を支援する役割を提案する。
人間のプロダクトオーナーは価値・優先順位・採否を決め、開発者は実現方法と見積もりを担う。
Pfのスクラムマスター役は進行支援・障害の可視化・振り返りの促進とし、人間の責任を自動的に代行しない。

## 用語と整理の基準

- 体験設計：実現したい体験。大きく変わりにくい前提。
- 設計原則（プリンシパル / Principal）：体験設計を根拠として具体仕様と実装要件を導く上位仕様。見直し可能。
- 断片／体系：整理状態を表す。設計原則は体系の内側に位置し、第三の整理状態にはしない。
- **再構築（レコンストラクション）**：断片と既存の体系を照合し、統合案を作り、確認を経て確定する過程。

再構築では体験設計・設計原則との関係、矛盾、重複、根拠不足を明示する。
推測で不足を埋めず、採用候補・保留と理由・人間への確認事項に分け、出典断片を保持する。

## 提案する運用

1. 計画時：未整理の断片と保留事項を示し、整理作業をスプリント候補へ挙げる。採用と優先順位は人間が決める。
2. 開発中：指示・観察・実験結果を断片に残す。Pfは未整理件数と阻害事項を示す。
3. レビュー前：スプリントに紐づく断片を対象に再構築案を自動生成する。現在の再構築はプロジェクト全体が対象なので、範囲指定は将来別途必要。
4. レビュー：人間が体験設計との整合と変更内容を確認し、採用・保留・再提案を決める。採用分だけ確定し、TODOを更新する。
5. 振り返り：保留の滞留、確認の負担、再提案の理由を材料に進め方の改善を提案する。プロダクトの採否とは分ける。

日次の通知や反復の強制、コードの自動変更、マージ、リリースはこの役割に含めない。

## 将来の状態と自動実行

整理待ち → 案生成中 → 確認待ち → 確定済み。保留した断片は整理待ちに残る。
生成失敗は理由を保存して再試行可能にし、確認待ちを完了扱いしない。
確認前に仕様や対象断片が変わった案は失効し、再生成を案内する。

イベントは「対象スプリントがレビュー準備へ移った」等の明示された状態遷移を候補とする。
冪等キーはプロジェクト・スプリント・イベントID・対象リビジョンから構成する。
プロジェクト単位の排他、永続的な実行記録、回数を制限した再試行を設け、同じイベントで案を重複生成しない。
権限失効やスプリント取消時は実行を止める。自動確定は行わず、現行owner/plannerの確認権限を維持する。
現行の一時的な生成排他だけでは、再起動をまたぐ自動運用を保証できないため追加設計が必要。

## 責務境界と採用時に決めること

Pfは仕様・出典・再構築案・整理状況の正本を持つ。
Actio等に既存の作業管理がある場合は、スプリントと実行タスクを二重管理せずIDで参照する方針を候補とする。
Ccのセッション管理、Schedula等のスケジューリングとの接続は既存契約を調査してから決める。
これらのサービス連携は未調査の設計候補であり、実装済みとは扱わない。

採用時には、スプリントの正本、断片の対象範囲、生成タイミング、通知先と頻度、費用上限、保留の再検討周期を決める。
導入は「手動の整理TODO」→「人間が起動するスプリント用提案」→「イベントによる案生成」の段階を候補とする。
今回実装するのは最初の断片整理TODOのみ。後続段階は別途承認後に実装する。
