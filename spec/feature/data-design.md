# データスキーマと論理保存先の設計

2026-09-08: neco の指示で「Cr の保存領域」はデータごとの論理的な保存先と確定。

Praeforma のプロジェクトから「データ設計」を開き、データセット・項目・型・参照・分類・保護方針・保存先を編集する。これは設計情報を管理する機能であり、設計を保存しても Cernere のテーブル作成・データ移動・権限変更は発生しない。

この機能の保存先設計はユーザーデータを対象とする。master / user の分類欄はあるが、マスターデータ専用の設計導線・スキーマ機能を代替しない。専用 UI の実装は `spec/tasks/2026-09-08-master-data-schema-designer.md` で別に扱う。

## 操作

- データセットに名前、識別名、目的、master / user、権威ソース、単一ユーザー行 / 複数レコードを設定する。
- 項目に識別名、型、必須、主キー、説明、他項目への参照を設定する。
- 項目ごとに保存先を選ぶ。未定、Cernere の共通プロフィール参照、Cernere のプロジェクト領域、サービス DB、ローカル、オブジェクトストレージを区別する。
- Cr プロジェクト領域は project key / module / column で指定する。module は分類・opt-out 単位で、別テーブルではない。物理 slug、DB URL、credential を指定する入力欄は設けない。
- 個人属性かどうか、保護要否、保護方法、読取主体、更新主体、保持・削除方針を項目ごとに記入する。
- 設計を保存・再読込し、設計 JSON と保存先一覧 Markdown をダウンロードできる。出力は設計書であり Cr の適用用スキーマではない。

## 不変条件

- PF-DATA-1: 閲覧はプロジェクトメンバー、編集は owner / planner / designer / programmer。全 API で認証・対象プロジェクト所属・論理削除を検査する。
- PF-DATA-2: 保存は expectedRevision による比較更新。初回の同時保存も一方だけ成立し、他方は 409。取得失敗を空データと扱わない。
- PF-DATA-3: データセット / 項目 ID は安定 UUID。重複 ID・識別名、存在しない参照、型の不一致は拒否する。UI の削除時は参照元を解除してから削除する。
- PF-DATA-4: 未定の保存先や未記入の保護方針は下書きとして保存できる。確認事項を画面・出力に残し、定義が完成したと偽らない。
- PF-DATA-5: Cr のユーザー領域は user データ用。プロジェクト領域は 1 ユーザー 1 行で、追加項目を主キーにはできない。Cr が扱えない型、予約列名、同じ project key / column の重複割当を拒否する。共通プロフィールは既存項目への参照として扱う。
- PF-DATA-6: 個人属性は user データ・保護必須・Cr 正本。未定の下書きは許すが、別の保存先へ設定済みにすることは拒否する。
- PF-DATA-7: Pf に保持するのは設計メタデータのみ。ユーザーの実値・認証 secret を保持する入力を設けず、local mode の固定 identity から Cr 管理者権限を導出しない。
- PF-DATA-8: API は構造・件数・本文サイズを制限する。SQL は固定のテーブル定義とパラメータ化された文だけを使い、設計中の識別子を DDL として実行しない。
- PF-DATA-9: 保存失敗・競合では入力を保持する。競合時は最新の保存内容を表示し、入力の書き出し後に利用者が明示して読み直せる。自動的に版だけ進めて再送しない。最新版を表示したうえでの明示操作に限り、入力を残したまま基準版だけを最新へ進めて保存し直せる。相手の変更が失われることを確認してから実行する。

共通契約は `shared/data-design.ts`、意味的な検証は `shared/data-design-validation.ts`。サーバーの Zod が構造を検証してから共通検証へ渡す。UI も同じ意味的検証を表示する。保存方式は既存の PostgreSQL / SQLite に対応し、プロジェクト単位の単一設計文書として扱う。
