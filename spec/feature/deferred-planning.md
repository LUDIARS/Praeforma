# デファードプランニング

## 目的と用語

2026-09-08 neco指示。Pfは仕様考案と設計に集中できる場所とし、AIに相談できる専用LLMウインドウを常に最前面へ表示できるようにする。

- **フラグメント (fragment)**: バイブコーディングでの指示、走り書き、Cc/Pfで指示した仕様などの断片情報。最初から整合性・分類・完全性を求めない。最終的にはシステムの一部に取り込まれるか、不要として消える。
- **ストラクチャード (structured)**: 相互に整合し、構造化された正規の仕様。システムの構成と仕様の対応を説明できる。
- **デファードプランニング (deferred planning)**: 断片を使って実装を進め、ある程度育ったプロダクトの断片群を後から構造化して正規の仕様として定着させる方法。
- **レコンストラクション (reconstruction)**: フラグメント仕様と既存の構造化仕様を統合し、再構築する処理。再構築の確定で新しい版になる。初回の構造化だけでなく、既存の正規仕様への追加・訂正・分割・統合を扱う。

## 確定している要件

1. 仕様画面をフラグメントとストラクチャードに分ける。
2. 実装済/未実装を仕様画面から管理する。
3. Cc/Pfで指示した仕様はすべてフラグメントに登録する。
4. フラグメントを蓄積してから構造化でき、最初に厳密な計画を要求しない。
5. レコンストラクションは既存構造化仕様も入力として再構築し、版を上げる。
6. 設計画面を使いながら専用LLMウインドウで相談できる。

## データモデル案

実装状態と構造化状態を別軸にする。実装済フラグメントも存在し、構造化しただけで実装済にはしない。現在のspecs.status (draft/review/approved/obsolete) は承認状態であり、実装状態へ流用しない。

| データ | 内容 |
| --- | --- |
| フラグメント | 安定ID、対象プロジェクト、原文、作者参照、受信元、受信元イベントID、日時、関連対象、訂正元ID |
| 処理結果 | 未整理・統合先仕様ID/版・不要として除外した理由。分割や複数仕様への統合も関連として保持 |
| 実装状態 | 実装済/未実装、更新者、確認対象の仕様版、根拠参照。既存データの移行時は未確認を明示し、承認済から実装済を推測しない |
| 構造化仕様 | 安定ID、ドメイン、要求本文、制約、受入条件、関連仕様、出所フラグメント、編集版 |
| 仕様セットの版 | プロジェクト単位の再構築版、親版、構造化仕様のスナップショット、確定者・日時、差分 |
| 再構築実行 | 入力フラグメントID、入力の構造化仕様版、生成案、統合/除外対応、未解決の矛盾、実行結果 |
| 相談 | プロジェクト単位の会話、発言者、本文、関連対象、フラグメントへの参照 |

既存spec.versionは編集競合検出に使っているため、再構築による仕様セットの版とは分ける。仕様内容が変わった場合は過去の実装根拠をそのまま最新版の根拠とせず、確認対象の版を示す。

## 指示の取り込み

- 原文を保存してから後続のAI処理へ渡す。AI処理が失敗しても入力を失わない。
- Pfの仕様登録・相談内の仕様指示・既存画面の仕様作成経路を共通の受信処理へ接続する。自由入力にはドメイン必須を課さず、構造化仕様の確定時に所属ドメインを求める。従来の構造化仕様APIのドメイン必須は維持する。
- Ccは仕様指示を受けた正規イベントの出所を渡す。PfのプロジェクトIDへの対応、送信者の権限、受信元イベントIDを検証する。対象が分からない指示を別プロジェクトへ推測で割り当てない。
- Cc側は永続的な送信待ち記録を持ち、Pf停止中も再送できる。Pfは受信元＋イベントIDで同じイベントの重複登録を防ぐ。同文の別指示を本文一致だけで消さない。
- 人間による仕様指示と、AI応答・自動通知・テストログは出所属性で区別する。AIの要約だけを保存して原文を捨てない。指示の訂正は訂正関係付きで記録する。
- 既存仕様は出自を偽って新しい人間指示として登録せず、移行元を明示して最初の構造化版へ取り込む。

## レコンストラクションの整合性

入力のフラグメント集合と構造化仕様の基準版を固定して案を作る。生成中に追加された指示は次の処理へ残す。

各フラグメントを統合先へ対応付けるか、理由付きで不要とするか、未解決として残す。AIが処理できなかった断片や矛盾を黙って削除しない。既存の仕様IDは維持可能な限り維持し、分割・統合時は旧IDとの関係を保存する。

確定は、基準版の比較更新・構造化仕様のスナップショット・フラグメント対応・版の加算を単一トランザクションで行う。同じ処理の再送で二重に版を上げない。基準版が変わった場合は競合として案を残し、再構築をやり直す。失敗・取消では正規版を更新しない。

不要になったフラグメントは通常一覧から除外する。追跡用の最小情報を残す案とし、原文の保持/削除操作は明示する。単にAIが不要と推測しただけで履歴を不可逆に消さない。

## LLM相談ウインドウ

プロジェクトの画面移動で会話を失わない。移動・サイズ変更・折り畳みを備え、設計画面と同時に使える。現在のプロジェクトと選択対象を明示し、会話が別プロジェクトへ混ざらない。

既存のCLI経由LLM呼出しを再利用候補とする。呼出し中・失敗・再送・取消を表示し、失敗時に架空の返答へ置き換えない。相談内容の保存と仕様指示のフラグメント登録を関連付ける。新しいLLM接続先・認証情報を推測で追加しない。

## 実装前に確認する点

- 最前面の範囲: Pf画面内の常駐パネルか、他アプリの上にも表示する独立ウインドウか。前者と後者は実装方式が異なる。
- 再構築の確定: AIが案を出して人が確認するか、処理完了時に自動確定するか。現時点の推奨案は人の確認後に確定する方式。

## 検証条件

- Cc/Pfの同一イベント再送で断片が重複せず、別イベントの同文指示は失われない。
- 受信・保存・再送の各障害で原文を失わず、別プロジェクトの読取・更新を拒否する。
- フラグメントを実装済にしても構造化済にはならず、再構築しても実装済を捏造しない。
- 再構築で元の構造化仕様と追加断片が統合され、差分・統合先・未解決事項を確認できる。
- 確定1回につき仕様セットの版が1回だけ上がる。競合・取消・LLM失敗は版を上げない。
- 画面移動・再読込・送信失敗でも相談の保存済み履歴と指示を失わない。

本書は設計定義であり、ここに記したAPI・DB・Cc自動登録・LLMウインドウはまだ実装していない。
