# シナリオとユーザー体験

SPEC-PF-SCENARIO-EXPERIENCE。シナリオは「やりたいことを流れに沿って書く」。

- PF-SCENARIO-1: やりたいことと、その結果ユーザーに届けたい体験を記述する。操作を伴わない鑑賞・雰囲気・演出も対象にする。
- PF-SCENARIO-2: カテゴリはゲームプレイと表現。ゲームプレイは画面遷移を表示・設定する。表現はシーン全体のグラフィックがどうなってほしいかを指示書として保存する。
- PF-SCENARIO-3: 各画面の基本構成はシーンを正本とする。シナリオの画面はシーンとフレームを参照し、追加パーツと遷移だけを保持する。基本構成を複製・上書きしない。既存の未関連付け画面は保持する。
- PF-SCENARIO-4: シナリオの変更は既存の revision 競合検出と根拠の再確認判定を通す。旧データのユーザー体験は未記入として表示し、自動で達成済みにしない。
- PF-OVERLAY-1: 組み込み可能なブラウザライブラリで仕様とテスト状況を表示する。明示した Pf 接続先・プロジェクトを使い、破棄時にリクエストと表示を解放する。
- PF-OVERLAY-2: アプリ側は Tela の別プロセスへ同じ確認内容を渡す。対象ウインドウの外へ張り出して表示し、対象の寿命に追従する。
- PF-OVERLAY-3: テスト未実施・失敗・過去の根拠を成功と表示しない。プロジェクト全体の最新テストとシナリオ単位の根拠を区別する。取得失敗を空の成功表示に置き換えない。
- PF-OVERLAY-4: Unity Editor 拡張はアクティブシーンを検知し、保存済み GUID 対応または一意な同名の Pf シーンから仕様を取得する。曖昧な場合は明示選択し、別シーンの仕様を継続表示しない。未保存シーンの選択はウインドウの寿命内だけ保持する。
- PF-OVERLAY-5: Unity では仕様と基本要素・追加パーツを GameView 上に Tela で表示する。オーバーレイのメニューから関連シナリオを排他選択し、基本要素は独立に表示切替できる。GameView の非表示・閉鎖、domain reload、Editor 終了時には非表示または破棄する。
- PF-OVERLAY-6: 「要素」「仕様」「実装・テスト」を分け、切替時もシナリオ選択を保持する。長文（280文字超または5行超）は見出しを残して初期状態では折りたたむ。展開後も全文を保持し、Tela は表示領域に合わせてページを分ける。
- PF-OVERLAY-7: 実装状況の正本は Actio のタスク／バックログ。タスク完了 → 人間確認 → 完了。追加バックログは差し戻し、仕様変更は再確認へ移る。Pf の根拠・テストを人間確認の代用にしない。
- PF-PROJECT-INDEX-1: 一覧の最上部に検索とチーム絞り込み、最下部に作成 UI を置く。検索は参加中プロジェクトの名前・説明・チーム ID を対象とし、ページ分割前に適用する。チーム候補も参加中プロジェクトから求める。
- PF-PROJECT-INDEX-2: 検索とチーム条件を localStorage に保存し、次回表示時に復元する。設定で無効化すると保存条件を消し、次回は未絞り込みになる。ストレージ利用不可でも当該画面の検索は継続できる。

## 確認 API

`GET /api/projects/:pid/review-overlay?layout_id=:lid` は viewer 以上の参加者に読み取り専用の
シーン・関連シナリオ・仕様・検証根拠・プロジェクト全体の受入テスト集計を返す。
シーン指定時の仕様は、その layout を対象とするものと対象未指定の全体仕様。
シナリオは canvas の scene_ref で関連付いたもの。シーンを省略するとプロジェクト全体。
`format=tela` は同じ内容の Tela 文書、`frame_id` はシーン内の対象画面（省略時は先頭）を選ぶ。
接続先・資格情報の取得は利用アプリが所有し、Tela 子プロセスへ資格情報を渡さない。
文書は明示更新または Unity シーン変更時に取得する。

本文は要素配置と別の表示にし、長文は折りたたみ、展開後の表示をページに分ける。Tela の現行公開形式上限（32 グループ・1024 要素）を超えた場合は
取得エラーとして表示し、途中までを正常表示しない。

## Actio 連携

`GET /api/projects/:pid/review-overlay/manifest` は同じ参加者認可で orgId を teamId として返し、仕様・シナリオの確認対象と fingerprint を公開する。
この経路は Actio を呼ばない。Actio が現在の仕様を読み取る入口なので、循環 HTTP 呼び出しを作らない。
fingerprint は本文だけでなく受入条件、対象、画面構成を含む。シナリオは use case/canvas と参照シーンを含む。
シナリオと仕様の直接関連が未定義のため、シナリオ確認はプロジェクト内の全仕様を依存対象とし、変更時には保守的に再確認を要求する。
基本構成が旧形式のままのシーンも実際の読み取り内容を fingerprint に含める。根拠・テスト結果そのものは仕様の版に含めない。

Pf サーバーに `PRAEFORMA_ACTIO_URL`、`PRAEFORMA_ACTIO_CLIENT_ID`、`PRAEFORMA_ACTIO_CLIENT_SECRET` を設定する。
URL は Actio のサービス所有 catalog から取得し、API クライアントは tasks scope を持つものを使う。
Pf の認証済み Cernere userId を `X-Decided-By` として渡し、Actio でも現在のチーム所属を検査する。
Pf の orgId と Actio teamId が一致することが必要。秘密情報はブラウザ・Unity・Tela 文書へ渡さない。
Actio 側は `PRAEFORMA_URL` / `PRAEFORMA_TOKEN` が必要で、本変更の仕様確認 API を利用する。
未設定・権限不足・不達・不正な応答は実装状況の取得不可として明示し、未登録や完了へ置換しない。
状態は更新・再取得時に現行仕様から評価される。人間確認やバックログの追加は Actio の計画画面で行う。
