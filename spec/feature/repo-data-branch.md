# 設計データの保存ブランチ

neco の決定 (2026-11-09): フラグメント、ストラクチャード、UX、シーン構造、シナリオの資料は、
コードの main とは別に、各リポジトリの専用ブランチ `pf-data` に 1 本で持つ。

## 目的

設計データの更新にコードの審査を挟まず、他の拠点やエージェントがリポジトリの取得だけで最新の設計を読めるようにする。

## ブランチの構成

```
pf-data.json     形式、プロジェクト、生成したファイルの一覧
fragments/       フラグメント (処理結果を含む)
structured/      仕様、対象、受け入れ条件、ドメイン、データ設計
ux/              UX の目的、境界の提案と判断、証拠
scenarios/       シナリオ、ユースケース、キャンバス
scenes/          レイアウト、配置、オブジェクト、シーン文書、遷移
```

人が直接追加したファイルは残す。Pf が消すのは前回自分が生成して今回生成しなかったファイルだけ。

## 動き

- `POST /api/projects/:pid/repo-data/publish` (owner / planner): DB の内容をブランチへコミットする。変更が無ければコミットしない。
- `GET /api/projects/:pid/repo-data`: 保存先とブランチの先頭を返す。
- `PUT /api/projects/:pid/repo-data/binding` (owner): プロジェクト名とフォルダ名が違うときの保存先を設定する。

保存先はリポジトリ置き場の一覧にあるフォルダだけで、リクエストから任意のパスは指定できない。
未設定の場合はプロジェクト名でフォルダを探し、見つからなければ `repo_data_dir_not_found` で失敗する。

作業ツリーとチェックアウトには触らない (git の内部コマンドで一時インデックスからコミットを作る)。
更新は比較付きで行い、途中で他の更新が入ったら `data_branch_moved` で失敗する。
利用者を特定する項目 (`*By`, `*UserId`, `*DisplayName`) はブランチに書かない。

## 第一段階に含めないもの

| 項目 | 状態 |
|---|---|
| リモートへの push | 認証の扱いが別途必要。人かリリース手順が push する |
| ブランチから DB への取り込み | 第二段階。別拠点の Pf が読むために必要 |
| `spec/ux/*.md` の移動 | Anatomia と Revisor が main から読むため、読み取り側の変更と AIFormat の規則変更が先 |
| 編集のたびの自動保存 | 第二段階。現在は明示の publish |
