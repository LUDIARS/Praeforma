# プロジェクトメニューと登録

- メニュー名は「概要 / UX/ゴール / ドメイン / アクター / シーン / 仕様」。内部の tab ID とディープリンクは維持する。
- 表示は4タブ＋「その他」。Memoria の4枠表示と同様に、その他から選んだタブは先頭に移す。ディープリンク先のタブも4枠内に表示する。
- 「その他」を閉じている間は、格納したタブをDOMに描画しない。開いたときだけ4枠に含まれないタブを表示し、選択・Escape・フォーカス離脱で閉じる。
- プロジェクト画面のタブバーは常に1個。タブバー・UX/ゴール・ドメインのReactキーは役割とプロジェクトIDで区別し、どの部品のスロットかを読み取れるようにする。キーの役割はプロジェクト変更時に入力状態をリセットすることであり、タブバーの重複防止ではない (重複の原因は未特定、spec/plan/problem_logs/2026-09-08-project-tab-overflow.md 参照)。
- 「ドメイン定義」ブロックは操作メニュー。コアドメイン登録・ビジネスドメイン登録・再取得を共通サイズの角丸ボタンで表示する。フォーム・定義編集・一覧はメニューブロックの外に置く。
- ドメインは説明付きボックス。コア／ビジネス／従来の未分類を分け、選択すると子ドメインを展開する。既存の parent_id を使用し、異なる分類の子も分類見出しを付ける。
- 登録時に名前、説明、価値、親ドメインを入力できる。名前と価値は必須。POST domains の任意の definition={kind,value} で分類と価値を同じINSERTに保存する。旧クライアントが definition を省略した場合は従来どおり未分類。
- アクターは名前・必須の所属ドメイン・説明を登録でき、説明付きボックスで一覧表示する。展開すると所属ドメインとその子ドメインを表示する。
- シーンは名前・種類・説明を登録し、一覧から配置編集へ進む。
- 仕様はドメイン・仕様コード・タイトルを必須とし、説明を入力できる。既存 spec_targets の domain 関連として保存する。POST specs は同じプロジェクトのドメインを最低1件要求する。既存の仕様の表示・編集は維持する。
- 送信中は操作を無効化する。失敗時は入力を維持し、成功時は該当一覧と関連するドメイン定義キャッシュを更新する。

## 検証

- 型チェックは web/server の既存コマンド。Revisor のローカル検証で新しい登録APIのSQLite永続化、無所属・別プロジェクトドメインの拒否、説明保持、親子保存を確認する。
- 本体への反映後、4＋その他、メニューと一覧の分離、分類・説明・階層展開、登録フォームの必須項目を確認する。
- 配信は Vite build の web/dist。サーバコードと SQLite ALTER を含むため、反映時は本体でビルドし Excubitor 経由で再起動する。

## Tela完成後の接続要件（未接続）

Telaの実装・接続契約が利用可能になった段階で、TelaからPfの登録・コメント・修正を行えるようにする。
現時点ではworkspaceのプロジェクト登録とPf内にTela実装を確認できていないため、架空のendpointや送信処理は作らない。

- データ正本はPf。TelaはPfのプロジェクト・対象IDを保持し、既存登録APIを利用する。仕様登録はドメイン必須を維持する。
- 修正はPfの権限と既存の版チェック（仕様 prev_version、ドメイン定義 expectedRevision）を使う。409時は入力を残して競合を表示する。
- コメントは対象との関連・投稿者・編集権限を伴う永続化契約を先に確定する。既存 feedback はアクター／シーン中心で、ドメイン／仕様への汎用コメントは接続前に対応範囲を確認する。
- Tela実装の利用可能通知後、接続先・認証・コメント対象を確認し、Tela側の操作から保存・再読込・権限拒否・競合まで通す。
